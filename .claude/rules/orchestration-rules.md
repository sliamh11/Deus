# Orchestration Rules
# Applies to all agent dispatch, pipeline automation, and task orchestration.
# Covers: issue creation, gate discipline, state management, MCP tool hygiene,
# warden co-gate verdict marking, session-start freshness, and pipeline co-authorship.
# Separated from core-behavioral-rules.md because these are pipeline-specific
# (not general coding/commit rules) and were triggered by observed failures:
# auth-error fallbacks labeled as "Scoped", agents working on stale requirements
# after mid-flight description changes, and double-escaped MCP tool output.

## Issue Creation
- Always assign issues to the correct project. Never leave issues floating without a project.
- Use actual newlines in descriptions — never `\n` escape sequences. MCP tools double-escape them, producing literal `\\n` in rendered output.

## Pipeline State Integrity
- If an issue's scope or description changes after entering the pipeline, move it back to the relevant step. Scope changed → back to the scoping step so the gate re-evaluates. Never leave an agent working on stale requirements.
- An issue may only advance past a gate when the gate agent ran successfully and approved. Any other outcome (error, timeout, crash, auth failure) is not approval — it's a failure that needs investigation or retry.
- The "Scoped" label may only be applied when the readiness gate produces a real scope block with enrichment. Fallback verdicts from failed gates are not scoping.
- **A Linear ticket showing `Done` means its PR merged — it does not mean the ticket's full scope is implemented.** Confirmed 2026-08-08 (LIA-519 roadmap): LIA-531 (credential-separation) merged and moved to `Done`, but its own PR body said "Design-only, implementation deferred to a future ticket" — a downstream session (LIA-536) nearly read "LIA-531 Done" as "activation-ready" for a dependent ruleset before catching the discrepancy by reading the merged PR's actual body, not just its Linear state. Before treating any `Done` ticket as clearing a real dependency, read the merged PR's own description for scope caveats ("design-only," "implementation deferred," "deliberately not touched") — the state field alone is not sufficient evidence of what shipped.

## Gate Discipline
- Gate fallbacks are errors, not approvals. If a gate agent fails, the verdict must be ERROR with a visible error label — never SHIP. Fallback-SHIP silently bypasses quality gates and produces false labels on unreviewed work.
- Never auto-advance an issue past a gate that didn't actually run. Silence is not consent.
- REVISE handling follows core-behavioral-rules.md: re-run after fixes until SHIP, no exceptions.
- Different warden roles/backends can reach opposite verdicts on the identical residual-risk judgment call — not a bucket/routing bug, a genuine disagreement (confirmed 2026-08-13, LIA-550/cliproxy credential fix: `threat-modeler` SHIPped a cleanup script's concurrency guard after 5 rounds, explicitly accepting the residual TOCTOU window as irreducible; the `code-reviewer` co-gate's GPT backend independently and repeatedly REVISE'd the identical window across 3 separate rounds, refusing to accept it). Treat the stricter verdict as controlling — do not override a specific, well-understood REVISE just because a different role/backend SHIPped the same risk. The correct resolution is to re-scope (split the disputed component out, ship the rest) rather than loop indefinitely trying to satisfy both, and rather than picking whichever verdict is more convenient. This is the same round-count-circuit-breaker instinct (`plan-review-rules.md`) applied to a cross-role disagreement instead of a single role's non-convergence.
- When a pipeline loop is detected, stabilize first: move the issue to a safe state (Manual Review Required or Backlog) before investigating. Never debug a live loop.
- The commit-gate string-matches `git commit` anywhere in a Bash command and blocks the ENTIRE command before any of it runs — this isn't limited to warden marks chained before a commit (a previously-documented case, in personal vault memory, not this repo); it also silently drops a leading `git add` in the same call, e.g. `git add -A && git status && git commit -m ...` never stages anything (confirmed 2026-08-08, checklist.design-integration PR #1133 — a code-reviewer pass caught the staged diff missing a fix that was genuinely present in the working tree). Always issue `git commit` as its own isolated Bash call, with `git add`/staging done in a prior, separate call — never chained with `&&` before it.

## Agent Dispatch
- Dispatched agents must work against the current issue state. If the issue was modified after dispatch, the agent's output is suspect — re-evaluate before accepting.
- Agent output that doesn't match the issue's acceptance criteria should not auto-merge, even if CI passes. The output-quality-gate exists for this.
- Failed dispatches (auth errors, container failures, timeouts) must be surfaced with clear error state — not silently swallowed.

## Tool Hygiene
- When creating or updating issues via MCP tools, verify the rendered output matches intent. Double-escaped markdown, broken formatting, and missing fields are bugs, not cosmetic issues — they degrade agent scoping and human review.

## Warden Co-Gate Verdict Marking
- The plan-review (edit) and code-review/verification/ai-eng (commit) gates decide on the verdict STORE (`.warden-verdicts.json`), not the marker files. The `run()` hook dispatcher resolves the bucket from the **hook EVENT's cwd** (`event["cwd"]`, which equals the committing session's working directory) and pins it via `worktree_override` for every gate runner — deliberately NOT the hook process's `os.getcwd()`, since the two can differ. Mark verdicts (both claude + gpt backends) into the bucket that matches that cwd, or the gate won't see them.
- cwd is the MAIN repo (`~/deus`, editing a worktree's files via `git -C <wt>`): the gate reads the FLAT `.claude/.warden-verdicts.json`. Mark from cwd=`~/deus` with NO `--worktree-root`.
- cwd is INSIDE a linked worktree (`EnterWorktree`, or Claude launched there): the gate reads the per-worktree `.claude/worktree-markers/<sha1(worktree_abspath)[:12]>/.warden-verdicts.json`. Mark from that cwd with NO `--worktree-root`, or from any cwd with `--worktree-root <wt>`. A flat mark is IGNORED here.
- Rule of thumb: match the bucket to the committing session's cwd — not "always flat" nor "always worktree". `--worktree-root` is only for an out-of-band writer whose cwd is not the gate's worktree (e.g. the gpt driver, or marking for a worktree you are not cwd'd into). If `mark`/`record-verdict` prints "cwd is not inside a worktree ... using the main-repo (flat) bucket", your mark went to the flat bucket — intended only for case 1.
- Mechanism (source of truth): `codex_warden_hooks.py` `run` (event-cwd → `worktree_override` for every gate runner), `_claude_marker_dir` (bucket resolution), `_current_worktree`/`_worktree_for_cwd` (cwd→worktree), `_with_cli_worktree` (CLI writer side), `run_warden_backends_gate` (gate read); `warden_hooks/verdict_store.py` `_verdicts_path`.
- SUPERSEDES RETRO-2026-06-17-02's "always mark from inside the worktree with `--worktree-root`": that is correct only for case 2, and post-#868/#869 the cwd-dependent rule above is canonical.
- Canonical recipe (avoids the bucket split): keep the committing session's cwd ON the worktree the commit targets — enter it via `EnterWorktree` (or commit from inside it) so the edit gate, the review agents, the marks, and the commit gate ALL resolve the same bucket from cwd, and mark with NO `--worktree-root`. Reserve `--worktree-root` for marking a worktree you are not cwd'd into. A `git -C <wt>`/`cd <wt> &&` commit from a main-repo session does NOT move the hook's cwd, so the gate reads the FLAT bucket while a `--worktree-root` mark lands in the worktree-sha bucket — the classic mismatch.
- Diagnostic: when the backends-gate blocks a model backend as "not run yet" but a SHIP for it exists in a different bucket, the block message now prints `co-gate bucket mismatch: a SHIP for <role>@<backend> exists in <dir>; this gate reads <dir> (worktree=...)` with the corrective re-mark — so a wrong-bucket mark is one clear message, not a silent retry loop (`_buckets_with_ship`, display-only, never changes acceptance).
- Agent-captured verdicts: the harness's Agent PostToolUse event carries the LAUNCH-dir cwd, not the session's EnterWorktree'd cwd, so the tracker routes by the worktree path named in the dispatch prompt (LIA-376, `_worktree_from_prompt`) and writes ONLY to that worktree's bucket. Name exactly ONE worktree path in every warden dispatch prompt, and make it the review target — an incidentally-named worktree receives the verdict (text routing cannot know intent). Zero or multiple named worktrees fall back to the event-cwd bucket.
- Re-review rounds: verdicts from a RESUMED agent (SendMessage) arrive as task-notifications no hook can see — the tracker keeps the stale round-1 verdict. Always dispatch a FRESH warden agent for each re-review round; a manual mark citing a resumed-agent SHIP is the exception, not the flow.
- Write-gate bucket mismatch for Workflow-dispatched subagents (LIA-446, distinct from the verdict-routing mechanism above): the plan-review-gate's PreToolUse hook decides gate applicability and which paths are "managed" from `event["cwd"]` alone (`_managed_paths` in `codex_warden_hooks.py`, via `_worktree_for_cwd(cwd, repo_root)`), even though it already extracts the edited file's own absolute path via `_event_paths`; the marker **bucket** itself is then resolved by `_claude_marker_dir`, which reads `_WORKTREE_OVERRIDE` (pinned from that same `event["cwd"]` by `run()`'s `worktree_override(wt)` context manager) — `_current_worktree`/`os.getcwd()` is only the no-override fallback, bypassed entirely in the gated path. A Workflow-dispatched subagent's reported cwd does not reliably track the worktree it was told to operate in (same root cause as the Agent-verdict-routing cwd gap above, but this is the separate write-time gate, not verdict capture) — a genuinely-in-worktree file can still get BLOCKED against the flat main-repo bucket even when a real per-worktree plan-reviewer SHIP already exists there, producing a misleading REVISE-shaped block that is actually an infra bucket mismatch, not a real plan defect. **Workaround, ONLY when a genuine per-worktree plan-reviewer SHIP already exists for that worktree: write via a Bash heredoc instead of the Edit/Write tool** — Bash-based file writes are not covered by this hook under the default plan-reviewer tool list (`Edit`/`Write`/`MultiEdit`/`apply_patch`/`ExitPlanMode`); if `Bash` is ever added to that list this workaround breaks. This bypasses only the redundant edit-time marker recheck; the commit-side code-review/verification/ai-eng gates still fire on the resulting diff regardless of write method, so it is not a general license to skip review — never use it to route around a REVISE or a missing SHIP. Build the heredoc pattern in from the start of any Workflow script that writes into a worktree from a dispatched subagent, rather than discovering it via a failed Edit/Write mid-run.
- **`--repo-root` gotcha (a distinct flag from `--worktree-root` above — do not conflate them):** `mark`'s/`mark-batch`'s `--repo-root` argparse option defaults to `Path(__file__).resolve().parents[1]` in `codex_warden_hooks.py` — i.e. it is derived from wherever the *invoked script file* physically sits, not from the main-repo path. Since git worktrees carry their own full checkout, running `python3 scripts/codex_warden_hooks.py mark ...` via a **relative** path with cwd inside a worktree resolves `__file__` to `<worktree>/scripts/codex_warden_hooks.py`, so the default `--repo-root` silently becomes the worktree itself — not the main repo. With `repo_root == worktree`, `_worktree_for_cwd(cwd, repo_root)` returns `top` (the worktree) directly via its `top == repo_root` branch — since `repo_root` here already equals the worktree, due to the flawed default — so `_current_worktree` resolves `wt` to the worktree without ever reaching its `or repo_root` fallback, and `_claude_marker_dir` takes its flat branch and writes `.warden-verdicts.json` / the `.plan-reviewed` touch-file to `<worktree>/.claude/` instead of `<main-repo>/.claude/worktree-markers/<sha1(worktree)[:12]>/`. The command still prints its normal success line and exits 0 — the misroute is invisible until the next gated Edit/Write in that worktree blocks again citing a still-missing SHIP. Always pass `--repo-root <main-repo-abspath>` explicitly when marking from a worktree cwd — this is exactly what the gate's own block-message remediation commands already do. The canonical recipe two bullets up (cwd on the worktree, no `--worktree-root`) still needs this flag too: `--repo-root` governs which repo `_claude_marker_dir` computes the bucket relative to, `--worktree-root` governs which bucket within that repo is chosen — two different axes of the same call. The specific `scripts/cogate.py`-based mitigation in this bullet is new; the "Warden Co-Gate Verdict Marking" section itself predates this addition (landed separately via #868/#869). Prefer `scripts/cogate.py` for co-gate marking when available — it sidesteps this gotcha structurally, calling `mark_warden(..., repo_root)` directly with `repo_root = primary_repo_root(wt)` (git `--git-common-dir`-based resolution) rather than going through the CLI's `__file__`-based default, so no `--repo-root` flag is needed when using it. The flag discipline above still applies to any direct `codex_warden_hooks.py mark`/`mark-batch` invocation.
- **`codex_warden.py --backend gpt --rev-range` gotcha (2026-08-07, codegraph-gate-retire/PR #1131):** omitting `--rev-range` defaults to `git diff HEAD` (working tree vs the pre-merge `HEAD`) — which is exactly what makes reviewing a merge-conflict-resolution commit dangerous mid-resolution (working tree already holds everything the merge brought in, while `HEAD` hasn't advanced past the pre-merge tip): the script treats everything `origin/main` brought in as brand-new content — including already-merged, unrelated work from other PRs — and can REVISE on real defects in that unrelated pre-existing content. Confirmed: it flagged 2 real bugs in ADRs merged via a separate, earlier PR. Passing a bare ref (no `..`) as `--rev-range` doesn't fix this either — e.g. `--rev-range origin/main` resolves to `origin/main^!` (that ref's own tip commit vs its first parent), reproducing the identical single-commit-diff bug against a different ref. Fix: always pass the full range form explicitly, `--rev-range origin/main..HEAD`; verify first with `git diff origin/main..HEAD --stat` to confirm the expected scope. Source: `scripts/cross_family_review.py:193-214` (`get_diff`).
- **`run` CLI dispatch smoke-test gotcha, closely related to the `mark`/`mark-batch --repo-root` trap above but for a different subcommand (2026-08-07, codegraph-gate-retire/PR #1131):** exercising a hook's real dispatch path pre-merge (since `warden-shim.sh` always execs the MAIN checkout's copy, per its own `WORKTREE_ROOT`/`REPO_ROOT` split — see `.claude/hooks/warden-shim.sh`) means invoking the WORKTREE's own unmerged script directly: `python3 <worktree>/scripts/codex_warden_hooks.py run <behavior> --repo-root <X>`. `--repo-root` here MUST be the main checkout, never the worktree — `.codegraph/codegraph.db` only exists there, never in a linked worktree. Passing the worktree as `--repo-root` doesn't error; the hook's own `db_path.is_file()`-style guards just return early with no log write, so every probe looks like a clean "PASS" when it never actually ran the logic under test. Confirm a smoke test is real, not a silent no-op, by checking `.claude/.warden-log` for a fresh line matching the expected behavior name. **Independently reconfirmed (LIA-534, 2026-08-08):** the SAME `warden-shim.sh` REPO_ROOT-anchoring produced a different-shaped false negative on a `run <hook-name>` PreToolUse gate invocation (not the `--repo-root`/codegraph-db case above) — two real invocations via the shim showed zero effect from a new gate-wiring change, misread at first as a code defect in the change itself, before tracing it back to this exact mechanism. The fix is the same: bypass the shim, invoke the worktree's own script directly with `--repo-root <main-repo-abspath>`.
- **Stage before marking, not after (2026-08-13, cliproxy-autocompact/PR #1185):** a co-gate verdict's `diff_hash` combines `git diff HEAD` (tracked content) with a sorted list of untracked file *paths* (existence only, not content) — `_compute_state_fingerprint`, `scripts/warden_hooks/verdict_store.py:152-212`. Marking a SHIP while a new file is still untracked (`git status` shows `??`), then `git add`-staging it afterward, moves that file from the path-list half of the fingerprint into the content-diff half — changing the hash either way, so the stored SHIP goes stale (`_fresh_entry`) and the commit-gate blocks as if nothing had been marked at all. Cost several repeated `cogate.py` re-runs in one session before catching the ordering. Fix: always `git add` everything the commit will include FIRST, then run `cogate.py`/`mark` against that fully-staged state, then commit — never mark against a diff that's about to change shape.
- **A configured backend with NO verdict BLOCKS; only a recorded verdict can fail open (2026-08-15, LIA-551):** the backends gate reads each role's backend list from the LOCAL, gitignored `.claude/wardens/config.json` (the tracked artifact is `config.json.example`). A backend in that list with no verdict at the current diff hash blocks with `<backend>: not run yet`, whereas a *recorded* `COULD_NOT_RUN` fails open by design. So a backend you cannot or will not run must be **removed from config**, not merely skipped — skipping it blocks every commit indefinitely. `scripts/cogate.py` only ever drives claude+gpt, so any third configured backend needs its own `python3 scripts/codex_warden.py --role <role> --backend <b> --warden-mark` run or it will block right after a clean `co-gate — PASS`. (glm was removed from `code-reviewer`'s list on 2026-08-15 for exactly this reason: z.ai returns HTTP 429, balance exhausted.)
- **`--claude-reason` is shell-interpolated (2026-08-15, LIA-551/PR #1187):** backticks inside the reason string are command-substituted before the script ever sees them, silently mangling the recorded reason (observed: an inline code span vanished and the shell emitted `command not found`). Avoid backticks in reason strings, or single-quote the whole value.
- **`plan-review-gate` (the Write/Edit-blocking gate, not just the commit-time gate) is also multi-backend co-gated** (2026-08-13): a bare `Write`/`Edit` call — not just `git commit` — can be blocked by `warden-backends-gate` demanding a GPT-backend `plan-reviewer` SHIP in addition to Claude's, via the same worktree-bucket mechanism this section documents for commit-time gates (confirmed against source: `scripts/codex_warden_hooks.py`'s `run_plan_review_gate` calls `_evaluate_backends("plan-reviewer", ..., skip_claude=True, ...)`). Confirmed via repeated live blocks: multiple `Write` calls were blocked with `[warden-backends-gate] BLOCKED: plan-reviewer is not SHIP across all configured backends`, requiring a manual `codex_warden.py --role plan-reviewer --backend gpt --content-file <path> --warden-mark` run before the Write would go through, even with a Claude-backend plan-reviewer SHIP already marked. Fix: after a Claude-backend plan-reviewer SHIP, before the first Write/Edit, also run the GPT-backend (and GLM if configured) equivalent with `--warden-mark` from the same worktree cwd — don't assume the single Claude-backend mark unblocks a Write.
- **A clean `co-gate plan-reviewer — PASS` can still be followed by `BLOCKED: no plan-reviewer approval marker` — cause NOT fully diagnosed (2026-08-16, observed three times in one session):** `cogate.py` printed `PASS  claude: SHIP  gpt: SHIP` naming the correct per-worktree bucket, and the very next `Write` was blocked by the plan-review gate. Listing that same bucket immediately afterwards showed `.warden-verdicts.json`, `.co-gate-loop-plan-reviewer.json` and `.plan-reviewer-cross-review.md` — but **no `.plan-reviewed`**. **Ruled out, by reading the code rather than assuming:** cogate.py failing to call the write. `cogate.py`'s step 2 calls `whooks.mark_warden("plan-reviewed", ...)` under `worktree_override(wt)`, and `mark_warden` unconditionally `.touch()`es the marker (`codex_warden_hooks.py:3480-3481`) immediately before the success line it prints; `.plan-reviewed` is in `_PER_WORKTREE_MARKERS` (`:480-487`) so `_marker` resolves it to the same per-worktree bucket the gate reads. **Also ruled out:** the two known invalidators — `run_session_init` (SessionStart) and `run_plan_mode_invalidator` (`ExitPlanMode` / a `Plan`-subagent dispatch). Neither fired between the mark and the blocked write, and both clear `.plan-reviewer-cross-review.md` alongside the marker (`cross_review_file`, `warden_review/constants.py:54-56`), which survived every time. **Also ruled out:** bucket mismatch — running the CLI `mark` afterwards writes `.plan-reviewed` into the *same* bucket hash cogate had just printed. So the divergence is between cogate's in-process `worktree_override` path and the CLI's own path, and remains unaccounted for. **Working remediation (all three times, first try):** run the gate's own printed command as its own Bash call — `python3 <main-repo-abspath>/scripts/codex_warden_hooks.py mark plan-reviewed SHIP "<reason>" --repo-root <main-repo-abspath>` — then confirm with `ls <bucket>/.plan-reviewed` rather than by re-reading the verdict JSON. Do NOT read this block as a bucket mismatch and start chasing `--worktree-root`: the verdicts are correctly bucketed, and the marker is the only thing missing.
- **`approve-admin-merge` without `--repo-root` prints success and exits 0 but does not satisfy the gate (2026-08-16, hit while admin-merging PR #1203):** `python3 <main-repo-abspath>/scripts/codex_warden_hooks.py approve-admin-merge --command '<cmd>'` printed `Approved one admin merge command for <main-repo-abspath>` — naming the right repo — yet the subsequent `gh pr merge --admin` was still blocked by `[admin-merge-gate]`, whose message reads as though no approval was ever issued. Same `__file__`-derived default as the `mark`/`mark-batch` trap above (`approve_parser`'s `--repo-root` default is `Path(__file__).resolve().parents[1]`, `codex_warden_hooks.py:3992`, identical in shape to `mark_parser`'s at `:4016`); invoking by absolute path is NOT sufficient to avoid it. Note `.admin-merge-approved` is deliberately excluded from `_PER_WORKTREE_MARKERS`, so it is always flat under `<repo_root>/.claude/` — `--repo-root` is the only variable in play. Always pass `--repo-root <main-repo-abspath>` explicitly. **This is a SECOND, distinct cause of the same symptom** documented under CI Verification Discipline (that gate hashes the LITERAL command string, so a trailing redirect breaks the match): there the fix is to re-copy the command verbatim, whereas here the command string was byte-identical across both attempts and only the approval call's `--repo-root` differed. Check both before concluding the approval simply failed to register. Cost one blocked merge attempt.

- **A cross-repo co-gate can print PASS while a backend reviewed nothing (2026-08-15, deus-v2 #86):** `scripts/cogate.py`'s GPT half resolves the diff from the LAUNCH repo, so for a change in another checkout it prints `[codex-warden] empty change — nothing to review (abstain)` and the summary still renders `gpt: SHIP` and `═══ co-gate <role> — PASS ═══`. The abstention is counted as an approval — the § Cross-Repo Worktree Handling gap producing a **false green**. Confirmed by re-running the identical gate with `--content-file <captured diff>`, which immediately returned a MAJOR finding the PASS had hidden (a platform check that would have silently omitted every verdict on Linux and Windows). **For any diff outside the launch repo, capture it to a file and pass `--content-file`, and read the backend's own output line — `abstain` is not a review.** Same discipline as `wait_for_checks.py`: the printed text is the signal, not the verdict banner. Mechanism, traced: `codex_warden.py:168-173` returns ABSTAIN with `verdict=SHIP` on an empty diff, `:316-323` records that SHIP under `--warden-mark`, and `cogate.py:178-179` prints PASS from the stored verdict regardless of the backend's exit code.

## Session-Start State Freshness
- Before treating local/worktree state as ground truth or implementing anything, run `git fetch origin` then `git --no-pager diff --stat HEAD origin/main`. Worktrees are pinned at creation and `origin/main` merges continuously (autonomous pipeline + work-fork), so a local checkout can be days behind.
- For any task that "needs implementing," first confirm it is not already on `origin/main` — a stale start otherwise reconstructs work that already shipped. Verify-don't-trust catches bad code before it lands, but the rediscovery cost is paid regardless; the fetch is the cheap defense.
- **`~/deus`'s own working directory staleness can silently break more than "what's implemented" checks — it can make a live infra test pass for the wrong reason** (2026-08-08, LIA-536): `com.deus.warden-opa` (the local OPA daemon) loads `scripts/warden_policy/policy/guardrails.rego` from disk at PROCESS START ONLY (no `--watch`, by design — see `opa-warden-attestations-v1.md`), from whatever `~/deus`'s working directory currently has on disk. Merging a PR to `origin/main` does NOT update `~/deus`'s own checkout or restart the daemon — those are separate, manual steps. Confirmed cost: a live end-to-end GitHub Actions test against this daemon "passed" (produced a plausible-looking deny) while the daemon was actually serving a policy version missing the Rego rule under test entirely — the deny came from the file's raw top-level default (`decision := {"allow": false, "reason": "guardrails policy produced no valid decision"}`), not from genuine evaluation of the rule being tested. Caught only by independently checking `curl -s http://127.0.0.1:8181/v1/policies | python3 -c "..."` for the expected rule content/marker string in the loaded policy, rather than trusting a plausible-looking pass/fail result. **A worktree-isolated session cannot fix this itself** — `git -C ~/deus fetch/merge` is sandbox-blocked (worktree isolation refuses git operations targeting a different checkout) — so this requires either the user or a non-worktree-isolated session running `git -C ~/deus fetch origin && git -C ~/deus merge --ff-only origin/main` followed by `launchctl kickstart -k gui/$(id -u)/com.deus.warden-opa` to reload. Before trusting ANY live test result against this daemon (not just "is the code implemented" checks), verify the loaded policy content directly.

## Autonomous Pipeline Co-Authorship
- The autonomous pipeline and work-fork are routine co-authors of `origin/main` and may merge work mid-session/overnight. Before building on or deploying their merged work: (i) re-check merge state via `mergeCommit`/`mergedAt` (not a stale "OPEN" read), (ii) for load-bearing surfaces (memory heart, gates) re-verify the controlling invariant first-hand, (iii) chain a distinct session log via `continues` — never overwrite the pipeline's logs on `/compress`.
- A pipeline merge is a hypothesis until verified first-hand, same as any delegated verdict (core-behavioral-rules.md § Verification & Honesty). Don't race the pipeline on its own PRs.

## Concurrent Session Collision
- Two Claude Code sessions can independently pick up the same stuck-job/handoff and start editing the same worktree's files concurrently, with no warning beyond the preflight hook's generic "N other live sessions" notice — this caused real, reproducible file-content oscillation during a review round on 2026-08-08 (codegraph-gate-retire/PR #1131: 3 dispatched review agents each independently confirmed a fix disappearing and reappearing from the same file). Don't assume single-writer just because you're the one in a worktree. When a review agent reports content that contradicts what you just read/verified yourself, check `ListAgents` and the preflight warning before assuming your own mistake or a flaky tool — a live peer session editing the same files by absolute path is a real, confirmed cause. Resolve via direct `SendMessage` coordination (ask, don't guess) rather than continuing to dispatch reviews against a moving target.

## CI Verification Discipline
- Never hand-roll a `gh pr checks --watch` remediation or a manual `gh pr view --json statusCheckRollup` polling loop — `scripts/ci/wait_for_checks.py <pr>` already exists (present in both `~/deus` and `~/deus-v2-mvp`) as the vetted, fail-closed replacement: it owns its own poll loop (never `--watch`), disambiguates "zero required checks reported" from "all green" (the exact listing-lag race that bit `--watch` twice in one session, 2026-07-21, PR #70 (deus-v2)), and returns an authoritative exit code (0 green / 5 not-green-or-timeout / 2 usage error) instead of a maskable one. Tunable via `DEUS_CI_POLL_INTERVAL`/`DEUS_CI_POLL_TIMEOUT`/`DEUS_CI_POLL_RETRIES` env vars, `--json`/`--compact` for agent-native output.
- **The script has no `--repo` flag and resolves the target from `gh`'s own cwd-based repo detection** (confirmed: its `argv` is `["gh", "pr", "checks", str(pr), "--json", ...]`, no repo scoping). Running it by absolute path from a session whose cwd is still a different repo (e.g. invoking `~/deus-v2-mvp/scripts/ci/wait_for_checks.py` while cwd is `~/deus`) silently checks the WRONG repo's PR of the same number. Always invoke it with cwd actually inside the target repo's checkout: `(cd <target-repo> && python3 scripts/ci/wait_for_checks.py <pr>)`, never by bare absolute path from an unrelated cwd.
- **If this script genuinely isn't available, do not hand-roll a simple fallback — a naive read reintroduces the exact race this section exists to prevent.** A single `gh pr view <pr> --json statusCheckRollup` read that only checks "every *reported* check's `conclusion` is `SUCCESS`" is NOT sufficient: during listing lag a required check can be entirely absent from the rollup (not failed, just not yet registered), and a naive read would wrongly conclude green because every check it *can see* passed. Any manual fallback MUST compare against the known set of required check names first (e.g. `gh api repos/<owner>/<repo>/branches/main/protection --jq '.required_status_checks.contexts'`, run with the same cwd/`--repo` scoping as above) and treat ANY expected-but-missing check as not-green (keep polling), not just check the ones present. If reproducing this correctly isn't straightforward in the moment, that is itself a signal to make `wait_for_checks.py` available (copy it into the target repo) rather than improvise — this exact mistake was caught by plan-review on the first draft of this very fallback bullet, which is the strongest evidence for why the vetted script, not a hand-rolled read, should be the only real path.
- **A background Task-tool completion notification's "exit code 0" summary can contradict the script's own printed output** (2026-08-07, codegraph-gate-retire/PR #1131): confirmed once — `scripts/ci/wait_for_checks.py`'s completion notification claimed exit 0 while the script's own stdout literally said `PR #1131: NOT GREEN — gh pr checks unreadable after 5 retries` (a transient `gh` API blip, not a real CI failure, but the notification alone would have been actively misleading if trusted). Always read the script's own printed output text, not just a task-notification's exit-code summary, before treating a CI/merge gate as satisfied.
- **A PR's `pull_request`-event CI can silently never trigger even though every plausible cause checks out healthy** (2026-08-08, LIA-523/PR #1132): confirmed across 3 separate pushes plus a `gh pr close`/`gh pr reopen` cycle — zero `event=pull_request` workflow runs ever appeared for that branch (checked directly via `gh api repos/<owner>/<repo>/actions/workflows/<id>/runs?event=pull_request`), while `pull_request_target`-triggered jobs (Labeler/Welcome) fired normally on the same pushes, other PRs' CI worked fine in the same window, `gh api repos/<owner>/<repo>/actions/permissions` showed Actions enabled, the workflow's own `state` was `"active"`, and a manual `gh run rerun` on an existing run succeeded instantly (ruling out billing/quota exhaustion — also moot on a public repo, which has unlimited Actions minutes regardless). Root cause never fully diagnosed (looks like a GitHub-side webhook-delivery gap scoped to that specific PR/branch, not the repo). The only fix that worked: open a **brand-new branch off the current `origin/main` tip**, cherry-pick the identical already-reviewed commit(s) onto it, open a **fresh PR**, and close the stuck one referencing it — `pull_request`-event CI then triggered normally on the very next push. Don't sink more than one close/reopen + one fresh push into diagnosing this before falling back to the new-branch/new-PR workaround; it costs one clean cherry-pick and is far cheaper than continued CI-outage archaeology, and there is no other confirmed fix.
- **The admin-merge approval gate (`codex_warden_hooks.py approve-admin-merge --command <string>`) hashes the LITERAL command string**, including any trailing shell redirects (2026-08-08): an approval issued for `gh pr merge <n> --repo <r> --squash --admin --delete-branch` did NOT satisfy a subsequent invocation of the same command with `2>&1` appended — the gate reported a generic "needs fresh explicit approval" block that read like the approval was simply missing, not that the hash didn't match. If a first admin-merge attempt is blocked immediately after what looked like a successful `approve-admin-merge` call, re-issue the approval using the EXACT command string about to be run (copy it verbatim, redirects included) rather than assuming the approval failed to register at all.
- **`scripts/ci/flag_lint.py` (the facade-prevention net-new-`DEUS_*`-flag citation check) diffs `base...HEAD` — i.e. the last COMMIT, not the working tree or staged index** (2026-08-08, LIA-536): running `python3 scripts/ci/flag_lint.py --base origin/main` locally after editing a file to add a required tracking-citation comment still reports the citation missing if that edit hasn't been committed yet, even with `git add` run. This produces a confusing "I already fixed this, why does it still fail" loop. Always commit (or at minimum verify via `git diff base...HEAD` matches the intended state) before re-running this specific linter locally to check a fix — `git status`/`git diff --cached` alone won't tell you why it's still failing.
- **The admin-merge approval gate's marker is consumed by the attempt, not the outcome** (2026-08-13): the `approve-admin-merge` approval is consumed as soon as the matching `gh pr merge --admin` command is attempted — even if that attempt fails for a completely unrelated reason (e.g. `GraphQL: Pull Request is still a draft`). Confirmed: a PR's merge was approved, failed only because the PR was still a draft (not yet marked ready for review), and the very next retry of the identical command was blocked again needing fresh approval. Fix: if an admin-merge attempt fails for any reason after approval, re-run `approve-admin-merge` with the exact same command string before retrying — don't assume the approval survives an unrelated failure.
- **The GPT co-gate backend's `COULD_NOT_RUN` (`codex_warden.py --backend gpt`, opaque `codex exec exited 1`) is the same failure class as GLM's known billing-exhaustion case, just less legible** (2026-08-08, LIA-531/PR #1151): the `codex_warden.py` wrapper reports a bare `codex exec exited 1` with no readable reason, which reads like a generic subprocess/infra fault — but running `codex exec` directly from the same worktree surfaces the real cause: `ERROR: You've hit your usage limit. ... try again at Aug 10th, 2026 3:23 PM.` (a quota/billing message, confirmed via direct probe). Confirmed by direct code read that `COULD_NOT_RUN` fails open for both backends simultaneously (`_evaluate_backends` in `codex_warden_hooks.py`: `continue`s without appending to `blocking`, no quorum/minimum-backends requirement) — so a commit can land on Claude's review alone if both GPT and GLM are down. This is the correct, by-design behavior, not a bug — but don't take an opaque `codex exec exited 1` at face value as a mystery infra fault; run `codex exec --sandbox read-only "<probe>"` directly once to read the real error before retrying blind. **The limit observed here was transient, not standing**: a real GPT SHIP came back on the same worktree/model roughly 10 minutes after the last `COULD_NOT_RUN`, despite the error citing a reset 2 days out — so don't extrapolate a fixed-future-date reset message into "stop retrying for the rest of the session." Retry once or twice with real spacing before falling back to fail-open; treat fail-open as the last resort, not the default response to one illegible failure.

## Documentation & Markdown Gotchas
- **`scripts/drift_check.py`'s ADR-freshness check (`parse_adr()`) only scans an ADR's first 20 header lines for a `**Scope:**` field** (2026-08-08, LIA-531/PR #1151): confirmed directly, `header = "\n".join(text.splitlines()[:20])`. A long-lived ADR whose header grows across many review rounds (Status/Revision-note paragraphs accumulating detail) can silently push `**Scope:**` past line 20 — the check then treats the ADR as missing Scope entirely, which fails the `--all` pre-push hook with `exit 1` and blocks the push. The failure message ("missing **Scope:** field") reads like the field was never added, not that it drifted out of the scan window. Fix: keep `**Scope:**` positioned early in the header (immediately after `**Date:**`, ahead of a long `**Status:**` paragraph) rather than in whatever order feels natural — the sibling ADRs in `docs/decisions/` already do this, worth matching proactively rather than discovering the 20-line limit at push time.
- **CommonMark converts a line ending inside an inline code span (backtick-delimited) into a literal space** (2026-08-08, LIA-531/PR #1151): a code span that wraps across a line break — e.g. `` `git-level-hard-backstop-\ndesign.md` `` — renders as `git-level-hard-backstop- design.md`, a corrupted identifier with a space where a hyphen should be. This is easy to introduce when hand-wrapping long prose paragraphs containing inline code references (filenames, function names) without checking where the wrap lands relative to backticks — and easy to miss in review, since the raw markdown source reads fine and only the *rendered* output is broken. Caught twice in the same session by two separate review passes at two different locations in the same file, the second only found by a file-wide scan after the first fix. Before shipping a long markdown doc with many inline code references, run a file-wide scan rather than eyeballing: `python3 -c "import re; from markdown_it import MarkdownIt; h=MarkdownIt('commonmark').render(open('<file>').read()); print([c for c in set(re.findall(r'<code>(.*?)</code>',h,re.S)) if re.search(r'[-/_.@]\s',c)])"` — a non-empty result means at least one code span is broken (verify each hit isn't a legitimate space, e.g. `gh api -X DELETE repos/…` correctly contains a space).

## Admin-Merge Branch Cleanup
- `gh pr merge --admin --delete-branch` can succeed at merging on GitHub while failing its own local post-merge step (`failed to run git: fatal: 'main' is already used by worktree at '<path>'`) whenever the invoking session's `main` checkout is a separate worktree — the common case in this repo, which runs many parallel worktrees off one bare/primary checkout. When that local step fails, the remote branch is silently left behind despite `--delete-branch` being passed (confirmed twice, 2026-08-03/04, PR #1106 and PR #1115 — identical failure both times).
- Always verify after any `--admin --delete-branch` merge: `gh pr view <pr> --json state,mergedAt,mergeCommit` to confirm the merge actually landed (it does, even when the branch-delete step errors), then check the branch is really gone: `gh api repos/<owner>/<repo>/branches/<branch>` (404 = clean; 200 = still present). If still present, delete it manually: `gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<branch>`.
- Don't treat the local git error as a merge failure — it isn't one. Don't retry the `gh pr merge` command on that error either (the PR is already merged; a retry just re-errors on "already merged").
- **Related but distinct**: personal memory `feedback_worktree_workflow.md` documents a different symptom of a related root cause — gh's local cleanup instead fails at `git branch -D <feature-branch>` (refused because that branch is checked out in its own worktree), recommending *omitting* `--delete-branch` entirely and doing manual `git push origin --delete` + `git worktree remove` + `git branch -D` afterward. This section's symptom is gh instead failing to `git checkout main` locally. Both are plausible depending on which worktree cwd `gh pr merge` is invoked from; either way, verify-after-merge (this section) is the safe fallback regardless of which local step fails.

## Cross-Repo Worktree Handling
- The `EnterWorktree` tool only manages worktrees of the session's *launch* repo. For a genuinely separate repo (e.g. working in `~/deus-v2-mvp` from a session launched in `~/deus`), it cannot create or enter worktrees there — confirmed via direct tool error ("not a registered worktree of <launch-repo-abspath>") 2026-07-21.
- Workaround: `git -C <other-repo> fetch origin` + `git --no-pager diff --stat HEAD origin/main` (session-start freshness, same as above) then `git -C <other-repo> worktree add .claude/worktrees/<name> -b <name> origin/main` manually, and pin absolute paths under that worktree for every subsequent Edit/Write/Bash call in this session.
- **None of the automated review gates provide real protection for cross-repo commits — confirmed by reading the mechanism, not assumed.** Two distinct, independently-verified gaps (2026-07-21):
  1. **`plan-review-gate` doesn't fire at all** for foreign-repo edits (`run_plan_review_gate`/`_managed_paths`: resolves the worktree from `event["cwd"]`, filters edited paths to that worktree — a foreign-repo absolute path fails the filter, gate returns a no-op). Confirmed both by code and by direct observation: 40+ Edit/Write calls into `deus-v2-mvp` worktrees in one session, zero blocks.
  2. **The commit-side gates (`run_warden_backends_gate`, used by code-review-gate and ai-eng-gate; verification-gate uses its own analogous `_read_verdict` check with the identical scoping flaw) DO trigger on the Bash command's text pattern regardless of target repo (`GIT_COMMIT_RE` matches `git -C <other-repo> commit ...`), but their SHIP-verdict lookup is entirely `repo_root`-scoped to the launch repo (`~/deus`)** — `_claude_marker_dir`/`_current_worktree` resolve the bucket from `cwd` mapped within `repo_root=~/deus`'s own worktree structure, with no branch for a foreign target repo at all. Practical consequence: if cwd is still anchored in a `~/deus` worktree (the common case — the workaround above only changes which repo's git commands you run, not the session's own cwd unless you separately track into it), a **stale, unrelated SHIP verdict sitting in that `~/deus` worktree's bucket can satisfy the gate for a completely unrelated foreign-repo commit** — the gate never reads the actual target repo's diff at all. `run_ai_eng_gate`'s own trigger check compounds this: `_diff_touches_llm_files(repo_root)` runs `git diff --name-only HEAD` with `cwd=repo_root` (the launch repo), so it inspects the LAUNCH repo's diff state, not the foreign repo's — a real diff touching LLM/prompt-sensitive files in the target repo can be silently missed, causing the ai-eng-gate to no-op when it should have fired.
  3. Matches the same class of gap `docs/decisions/hook-dispatch-facade-correction.md` names for a different trigger ("gate logic is backend-neutral; trigger is 100% Claude Code → non-Claude backends run unguarded") — here, trigger-text-matching is real but the substantive check underneath is scoped to the wrong repo, which is a more dangerous shape than an absent trigger: it can look like review happened (block message absent, or a SHIP found) when it didn't check the right thing.
- **Consequence: NO hook in this repo can be trusted to gate a cross-repo commit correctly today.** For work in a foreign repo, self-impose the FULL review discipline manually and explicitly: dispatch `plan-reviewer` before implementation, `code-reviewer` (and `ai-eng-warden`/`verification-gate` if the diff's content warrants them) before committing — reviewing the ACTUAL target-repo diff, not relying on any hook block/SHIP state to mean real review happened. This is out of scope for this rule addition to fix at the hook-resolution level; see LIA-467 for the tracked follow-up (real fix likely needs `run_warden_backends_gate`/`_diff_touches_llm_files`/`_claude_marker_dir` to resolve `repo_root` from the actual `git -C`/`gh --repo` target in the command text, not just the launch repo).
- **The foreign repo is not always one we own.** Everything above assumes the cross-repo target is another repo under our own control (e.g. `deus-v2-mvp`) where we can push and merge freely once review is self-imposed. A distinct case (confirmed 2026-08-08, LIA-529, `~/.hermes/hermes-agent`): the target's only git remote is a genuine third-party open-source upstream (`git remote -v` showed `origin` pointing at `github.com/NousResearch/hermes-agent`, no personal fork). In that case the self-imposed review discipline above still applies before committing, but publishing is a materially different, higher-stakes step than a normal cross-repo push: (1) check `git remote -v` before assuming any push/merge control at all, (2) if the only remote is a third-party org with no personal fork, forking (`gh repo fork <owner>/<repo>`) and opening a PR is the correct mechanism — communication with an upstream you don't own happens through PRs/issues, nothing else, (3) treat opening that fork+PR as needing the user's explicit go-ahead (it publishes to a real public org, not infra we control) even under a broad autonomy grant, and (4) merge authority belongs entirely to the upstream's own maintainers — "CI green" on our PR is not a merge signal there the way it is in `~/deus`, and no amount of self-imposed review substitutes for their review.
- **Dispatching an autonomous `claude --bg` session into a foreign repo with no `.claude/settings.local.json` of its own silently inherits the global `~/.claude/settings.json` permission mode** (confirmed 2026-08-08, LIA-529 dispatch into `~/.hermes/hermes-agent`): this repo's own `settings.local.json` sets `defaultMode: bypassPermissions`, but a foreign repo with no such file falls through to the global default — which on this machine is `dontAsk` (allowlist auto-deny, not "skip the prompt," per `~/.claude/CLAUDE.md`'s Permission modes note). A background session dispatched this way would silently stall, denied on nearly every tool call, with no interactive prompt to catch it. Check the target repo for its own `.claude/settings.local.json` before dispatching (`grep defaultMode <target>/.claude/settings*.json`); if absent, pass `--dangerously-skip-permissions` explicitly on the `claude --bg` invocation rather than assuming the launch repo's permissive default carries over — but only for a repo you actually trust (your own checkout, a fork you control, per the "foreign repo is not always one we own" caveat above). A genuinely untrusted third-party clone can carry its own hooks/executable content, and a bypassed permission check gives that content unrestricted host-side action; for that case, fix the underlying `dontAsk` allowlist gap or get explicit user authorization instead of reaching for the blanket bypass flag.
- **A fix implemented in a third-party fork needs its own scrub pass for private/internal references before committing — `code-review-rules.md`'s `no-hardcoded-personal` rule already covers this ("personal project IDs" is in its own Check text) but nothing *triggers* it automatically on a foreign repo, since the hooks don't meaningfully gate cross-repo commits (see the bullet above on automated review gates providing no real protection here) — it only fires if a `code-reviewer` is dispatched manually and happens to check for it.** Confirmed 2026-08-09, LIA-541 (`~/.hermes/hermes-agent`): a first-round implementation left 9 references to a private Linear ticket ID (3 in `hermes_cli/plugins.py`, 3 in `agent/shell_hooks.py`, 2 in `agent/outbound_webhooks.py`, plus the new test's filename), and separately, Deus-specific jargon ("warden gate" — a term meaningless to Hermes, which only knows generic "shell hooks"), scattered across production source comments/docstrings. Caught only because a manual `code-reviewer` dispatch cross-checked the repo's own convention (`GH-NNNNN` issue references, confirmed via `grep` against existing code) against what had actually been written — a `git commit` alone would have shipped it. Before committing to any third-party repo, grep the full diff for the originating tracker's ID pattern (e.g. `ABC-\d+`) and for the home project's own internal terminology, not just for secrets/credentials.
- **Nested-worktree creation via relative path** (2026-08-13): running `git worktree add <relative-path> -b <branch> <ref>` from inside an already-active worktree resolves the relative path against that worktree's own cwd, not the main repo — silently creating a worktree nested inside another worktree's directory (e.g. `.claude/worktrees/A/.claude/worktrees/B` instead of `.claude/worktrees/B` as a sibling). Confirmed by direct reproduction: `git worktree add .claude/worktrees/show-me-skill-import ...` from inside worktree `i-have-adhd-integration` created the worktree at `.../i-have-adhd-integration/.claude/worktrees/show-me-skill-import`. Fix: when creating a second worktree from inside an already-active one, always use a `~`-anchored absolute path (e.g. `~/deus/.claude/worktrees/<name>`), never a relative one.
- **`!`-prefixed commands don't escape worktree isolation** (2026-08-13): telling the user to run a command themselves via the `! <command>` prefix does NOT bypass the current session's worktree isolation — `!` still routes through this same session, so a command like `git -C ~/deus fetch ...` issued via `!` while the session is pinned to a worktree gets the identical "git operations must target its own worktree" refusal as if issued directly. Confirmed: exact scenario reproduced, with the harness surfacing it as a `<bash-input>`/`<bash-stderr>` block. Fix: a command that genuinely needs to run against the main checkout (not the worktree) needs either the user's own separate terminal (outside Claude Code entirely) or the session calling `ExitWorktree` first.

## Multi-Thread Work Mapping (Wayfinder-Inspired)
- For a loose idea too big for one session — multiple dependent-but-distinct threads branching off a single ask (e.g. "ship deus-v2's UI": research → TUI spike → TUI follow-up → web spec → infra follow-ups) — don't let related Linear issues stay scattered with only loose links between them. Adapted from `mattpocock/skills`' `wayfinder` skill (evaluated 2026-07-21, pattern borrowed rather than the skill installed — see the session log for the full comparison against this repo's existing Linear pipeline).
- Create one index issue (or Linear project doc) per multi-thread effort that tracks, in one place: what "done" looks like, decisions already resolved (one-line summaries + links to their issues), open questions still too fuzzy to ticket ("fog" — explicitly named as unresolved, not silently assumed), and what's consciously out of scope. Update it as threads resolve or new ones branch off — this is an index that gists and links, it never restates what's already recorded in the linked issues/session logs.
- Distinguish a **decision to make** from **work to execute** before ticketing it. A ticket should be a sharply-defined question ("should X use profile A or B") sized for one session, not a vague slice of the destination. This is the same discipline `core-behavioral-rules.md`'s "don't solve problems that don't exist yet" already asks for, applied to planning granularity specifically.
- This composes with `linear-slice` (tracer-bullet vertical slices) rather than replacing it — `linear-slice` handles decomposing an already-scoped plan into dependency-ordered execution issues; this section is about the earlier step of keeping the still-fuzzy, multi-thread *planning* state visible and current instead of scattered across chat history and disconnected issues.
