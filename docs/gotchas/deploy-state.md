# Session-Start State Freshness

**Read this when you are deploying, restarting a daemon, or about to trust a live test against local infra.**

Moved verbatim out of `.claude/rules/orchestration-rules.md` (which is
always-loaded, and was over Claude Code's 40.8k per-file limit) so it loads
only when the task calls for it. No rule below has been reworded.
Routed by [`.mex/ROUTER.md`](../../.mex/ROUTER.md); index at
[`docs/gotchas/INDEX.md`](INDEX.md).

- **`~/deus`'s own working directory staleness can silently break more than "what's implemented" checks — it can make a live infra test pass for the wrong reason** (2026-08-08, LIA-536): `com.deus.warden-opa` (the local OPA daemon) loads `scripts/warden_policy/policy/guardrails.rego` from disk at PROCESS START ONLY (no `--watch`, by design — see `opa-warden-attestations-v1.md`), from whatever `~/deus`'s working directory currently has on disk. Merging a PR to `origin/main` does NOT update `~/deus`'s own checkout or restart the daemon — those are separate, manual steps. Confirmed cost: a live end-to-end GitHub Actions test against this daemon "passed" (produced a plausible-looking deny) while the daemon was actually serving a policy version missing the Rego rule under test entirely — the deny came from the file's raw top-level default (`decision := {"allow": false, "reason": "guardrails policy produced no valid decision"}`), not from genuine evaluation of the rule being tested. Caught only by independently checking `curl -s http://127.0.0.1:8181/v1/policies | python3 -c "..."` for the expected rule content/marker string in the loaded policy, rather than trusting a plausible-looking pass/fail result. **A worktree-isolated session cannot fix this itself** — `git -C ~/deus fetch/merge` is sandbox-blocked (worktree isolation refuses git operations targeting a different checkout) — so this requires either the user or a non-worktree-isolated session running `git -C ~/deus fetch origin && git -C ~/deus merge --ff-only origin/main` followed by `launchctl kickstart -k gui/$(id -u)/com.deus.warden-opa` to reload. Before trusting ANY live test result against this daemon (not just "is the code implemented" checks), verify the loaded policy content directly.

- **A plist on disk is not a loaded agent — `ls ~/Library/LaunchAgents/` proves INSTALLED, never LOADED** (2026-08-16, LIA-552): a disabled or unloaded launchd job leaves its plist in place indefinitely, so the file's existence says nothing about whether anything is running. Only `launchctl list <label>` (its exit code) or the full `launchctl list` shows what is actually loaded. Confirmed cost: `com.deus-v2.morning-report.plist` is present on disk, and I reported it as merely "never bootstrapped" — it is in fact **deliberately** unloaded, because `docs/decisions/deus-v2-archival.md` (Accepted 2026-08-15) states "The `com.deus-v2.*` launchd jobs are disabled and unloaded". On the strength of the plist alone I offered the user a choice ("pull deus-v2 and load its agent") that was directly contrary to an ADR accepted the previous day. Check `launchctl list`, and for any job whose absence looks surprising, check whether a decision record explains it before proposing to (re-)enable it. This is the launchd-shaped instance of the same "merged is not deployed" gap the OPA bullet above documents: there, the daemon was running stale content; here, the job was not running at all while its plist suggested otherwise.

- **The `service` setup step rewrites every plist but does NOT reload an already-running job — and still reports success** (2026-08-16, LIA-552): the step is `npx tsx setup/index.ts --step service` (what the `/setup` skill runs; bare `npm run setup` just exits 1 with a usage error, `setup/index.ts:45-49`). Its `run()` (`setup/service.ts:24-80`) calls `setupLaunchd`, `setupLogReviewLaunchd` and `setupOAuthRefreshLaunchd`, then loops `installScheduledJobLaunchd` over every `SCHEDULED_JOBS` entry — never a narrow single-job installer. But `setupLaunchd` (`:129-136`) and `installScheduledJobLaunchd` (`:961`) both run a bare `launchctl load` with **no prior `unload`/`bootout`**, each in a `try/catch` whose only failure path is a `logger.warn` ending "(may already be loaded)" — worded differently at each site (`:135`, `:255`, `:966`, the last spec-interpolated), so grep that suffix rather than a whole line. Against a live daemon that load is a no-op, and the step still emits `STATUS: 'success'` unconditionally (`:149-156`) with `SERVICE_LOADED` derived from `launchctl list` containing the label — true whether or not anything was actually reloaded. So the OLD process keeps serving WhatsApp/Telegram/Slack/Discord/Gmail and nothing surfaces an error. Compare `setupOAuthRefreshLaunchd` (`:318-329`), the one function that does `bootout` *then* `bootstrap`, commented "bootout any stale instance first so bootstrap doesn't fail with 'already loaded'" — the author knew the workaround and did not apply it to the other two. The trap is the reverse of the intuitive one: **running setup after a code change can leave the old build serving traffic while looking like a successful deploy** — pair it with an explicit `launchctl kickstart -k gui/$(id -u)/com.deus` (or `bootout`+`bootstrap`) and verify the PID actually changed. For a SINGLE new scheduled job, skip the step entirely: generate that one plist via the exported `buildScheduledJobPlist` (the same function `installScheduledJobLaunchd` uses at `:941-968`) and `launchctl load` just that label.
