# CI Verification Discipline

**Read this when you are waiting on CI, reading PR checks, or gating a merge on green — which is every PR, not only deployment work.**

Moved verbatim out of `.claude/rules/orchestration-rules.md` (which is
always-loaded, and was over Claude Code's 40.8k per-file limit) so it loads
only when the task calls for it. No rule below has been reworded.
Routed by [`.mex/ROUTER.md`](../../.mex/ROUTER.md); index at
[`docs/gotchas/INDEX.md`](INDEX.md).

- Never hand-roll a `gh pr checks --watch` remediation or a manual `gh pr view --json statusCheckRollup` polling loop — `scripts/ci/wait_for_checks.py <pr>` already exists (present in both `~/deus` and `~/deus-v2-mvp`) as the vetted, fail-closed replacement: it owns its own poll loop (never `--watch`), disambiguates "zero required checks reported" from "all green" (the exact listing-lag race that bit `--watch` twice in one session, 2026-07-21, PR #70 (deus-v2)), and returns an authoritative exit code (0 green / 5 not-green-or-timeout / 2 usage error) instead of a maskable one. Tunable via `DEUS_CI_POLL_INTERVAL`/`DEUS_CI_POLL_TIMEOUT`/`DEUS_CI_POLL_RETRIES` env vars, `--json`/`--compact` for agent-native output.

- **The script has no `--repo` flag and resolves the target from `gh`'s own cwd-based repo detection** (confirmed: its `argv` is `["gh", "pr", "checks", str(pr), "--json", ...]`, no repo scoping). Running it by absolute path from a session whose cwd is still a different repo (e.g. invoking `~/deus-v2-mvp/scripts/ci/wait_for_checks.py` while cwd is `~/deus`) silently checks the WRONG repo's PR of the same number. Always invoke it with cwd actually inside the target repo's checkout: `(cd <target-repo> && python3 scripts/ci/wait_for_checks.py <pr>)`, never by bare absolute path from an unrelated cwd.

- **If this script genuinely isn't available, do not hand-roll a simple fallback — a naive read reintroduces the exact race this section exists to prevent.** A single `gh pr view <pr> --json statusCheckRollup` read that only checks "every *reported* check's `conclusion` is `SUCCESS`" is NOT sufficient: during listing lag a required check can be entirely absent from the rollup (not failed, just not yet registered), and a naive read would wrongly conclude green because every check it *can see* passed. Any manual fallback MUST compare against the known set of required check names first (e.g. `gh api repos/<owner>/<repo>/branches/main/protection --jq '.required_status_checks.contexts'`, run with the same cwd/`--repo` scoping as above) and treat ANY expected-but-missing check as not-green (keep polling), not just check the ones present. If reproducing this correctly isn't straightforward in the moment, that is itself a signal to make `wait_for_checks.py` available (copy it into the target repo) rather than improvise — this exact mistake was caught by plan-review on the first draft of this very fallback bullet, which is the strongest evidence for why the vetted script, not a hand-rolled read, should be the only real path.

- **A background Task-tool completion notification's "exit code 0" summary can contradict the script's own printed output** (2026-08-07, codegraph-gate-retire/PR #1131): confirmed once — `scripts/ci/wait_for_checks.py`'s completion notification claimed exit 0 while the script's own stdout literally said `PR #1131: NOT GREEN — gh pr checks unreadable after 5 retries` (a transient `gh` API blip, not a real CI failure, but the notification alone would have been actively misleading if trusted). Always read the script's own printed output text, not just a task-notification's exit-code summary, before treating a CI/merge gate as satisfied.

- **A PR's `pull_request`-event CI can silently never trigger even though every plausible cause checks out healthy** (2026-08-08, LIA-523/PR #1132): confirmed across 3 separate pushes plus a `gh pr close`/`gh pr reopen` cycle — zero `event=pull_request` workflow runs ever appeared for that branch (checked directly via `gh api repos/<owner>/<repo>/actions/workflows/<id>/runs?event=pull_request`), while `pull_request_target`-triggered jobs (Labeler/Welcome) fired normally on the same pushes, other PRs' CI worked fine in the same window, `gh api repos/<owner>/<repo>/actions/permissions` showed Actions enabled, the workflow's own `state` was `"active"`, and a manual `gh run rerun` on an existing run succeeded instantly (ruling out billing/quota exhaustion — also moot on a public repo, which has unlimited Actions minutes regardless). Root cause never fully diagnosed (looks like a GitHub-side webhook-delivery gap scoped to that specific PR/branch, not the repo). The only fix that worked: open a **brand-new branch off the current `origin/main` tip**, cherry-pick the identical already-reviewed commit(s) onto it, open a **fresh PR**, and close the stuck one referencing it — `pull_request`-event CI then triggered normally on the very next push. Don't sink more than one close/reopen + one fresh push into diagnosing this before falling back to the new-branch/new-PR workaround; it costs one clean cherry-pick and is far cheaper than continued CI-outage archaeology, and there is no other confirmed fix.

- **The admin-merge approval gate (`codex_warden_hooks.py approve-admin-merge --command <string>`) hashes the LITERAL command string**, including any trailing shell redirects (2026-08-08): an approval issued for `gh pr merge <n> --repo <r> --squash --admin --delete-branch` did NOT satisfy a subsequent invocation of the same command with `2>&1` appended — the gate reported a generic "needs fresh explicit approval" block that read like the approval was simply missing, not that the hash didn't match. If a first admin-merge attempt is blocked immediately after what looked like a successful `approve-admin-merge` call, re-issue the approval using the EXACT command string about to be run (copy it verbatim, redirects included) rather than assuming the approval failed to register at all.

- **`scripts/ci/flag_lint.py` (the facade-prevention net-new-`DEUS_*`-flag citation check) diffs `base...HEAD` — i.e. the last COMMIT, not the working tree or staged index** (2026-08-08, LIA-536): running `python3 scripts/ci/flag_lint.py --base origin/main` locally after editing a file to add a required tracking-citation comment still reports the citation missing if that edit hasn't been committed yet, even with `git add` run. This produces a confusing "I already fixed this, why does it still fail" loop. Always commit (or at minimum verify via `git diff base...HEAD` matches the intended state) before re-running this specific linter locally to check a fix — `git status`/`git diff --cached` alone won't tell you why it's still failing.

- **The admin-merge approval gate's marker is consumed by the attempt, not the outcome** (2026-08-13): the `approve-admin-merge` approval is consumed as soon as the matching `gh pr merge --admin` command is attempted — even if that attempt fails for a completely unrelated reason (e.g. `GraphQL: Pull Request is still a draft`). Confirmed: a PR's merge was approved, failed only because the PR was still a draft (not yet marked ready for review), and the very next retry of the identical command was blocked again needing fresh approval. Fix: if an admin-merge attempt fails for any reason after approval, re-run `approve-admin-merge` with the exact same command string before retrying — don't assume the approval survives an unrelated failure.

- **The GPT co-gate backend's `COULD_NOT_RUN` (`codex_warden.py --backend gpt`, opaque `codex exec exited 1`) is the same failure class as GLM's known billing-exhaustion case, just less legible** (2026-08-08, LIA-531/PR #1151): the `codex_warden.py` wrapper reports a bare `codex exec exited 1` with no readable reason, which reads like a generic subprocess/infra fault — but running `codex exec` directly from the same worktree surfaces the real cause: `ERROR: You've hit your usage limit. ... try again at Aug 10th, 2026 3:23 PM.` (a quota/billing message, confirmed via direct probe). Confirmed by direct code read that `COULD_NOT_RUN` fails open for both backends simultaneously (`_evaluate_backends` in `codex_warden_hooks.py`: `continue`s without appending to `blocking`, no quorum/minimum-backends requirement) — so a commit can land on Claude's review alone if both GPT and GLM are down. This is the correct, by-design behavior, not a bug — but don't take an opaque `codex exec exited 1` at face value as a mystery infra fault; run `codex exec --sandbox read-only "<probe>"` directly once to read the real error before retrying blind. **The limit observed here was transient, not standing**: a real GPT SHIP came back on the same worktree/model roughly 10 minutes after the last `COULD_NOT_RUN`, despite the error citing a reset 2 days out — so don't extrapolate a fixed-future-date reset message into "stop retrying for the rest of the session." Retry once or twice with real spacing before falling back to fail-open; treat fail-open as the last resort, not the default response to one illegible failure.

- **`scripts/ci/wait_for_checks.py` can NEVER return green on `liam-cyberpro/Deus`, and its failure text names the wrong problem** (PR #52, merged 2026-08-23 per GitHub; reproduced again on PR #57): it reports `NOT GREEN - gh pr checks unreadable after 5 retries` and exits 5 on a PR whose checks are all passing. "Unreadable" reads as a `gh` outage and `NOT GREEN` reads as a CI failure; it is neither. **Confirmed mechanism, driven end to end:** the script queries `gh pr checks <pr> --json ... --required`. This repo is private with no GitHub Pro, so branch protection cannot be enabled at all (`gh api repos/liam-cyberpro/Deus/branches/main/protection` -> `403 Upgrade to GitHub Pro or make this repository public`), which means **no branch here ever has required checks**. `gh` then writes `no required checks reported on the '<branch>' branch` to STDERR and leaves STDOUT EMPTY; `wait_for_checks.py` treats a stdout that does not start with `[` as an unreadable read, returns `None`, and after the retry budget emits the message above. It is **deterministic and repo-wide, not transient and not related to checks being pending** - a readable-but-pending query takes a different branch that sleeps and retries, and can never produce this string. Do NOT "re-test against a pending PR"; pendency is not the variable, required-vs-not is. **Why this matters more than a confusing message:** `.claude/rules/orchestration-rules.md` (CI Verification Discipline) mandates this script as THE merge gate for every PR, so on this repo the mandated gate structurally cannot pass. Until that is reconciled, verify with a bare `gh pr checks <pr> --repo <owner>/<repo>` (no `--required`), which returns the full table correctly, and gate on `mergeStateStatus=CLEAN`. This is a DIFFERENT cause from the 2026-08-07 note above, which attributed the identical string to a transient `gh` API blip - two distinct causes produce the same text, so a direct read is the only way to tell them apart.

- **FIXED (LIA-139): the cause above was a ROUTING bug, and the branch that should have handled it already existed but was unreachable.** `wait_for_checks.py` always had an `if not required:` zero-required-checks branch. `_query_checks()` returned `None` for BOTH "gh could not be read" and "gh says this branch has no required checks", and the caller routed `None` into the transient-retry bucket — so the zero-checks branch never once executed and every PR died on the retry budget instead. The fix distinguishes gh's signature (non-zero exit, EMPTY stdout, `no required checks` on STDERR) from a genuine read failure via a `NO_REQUIRED_CHECKS` sentinel, and routes it to a named state-(c) path: re-query WITHOUT `--required`, require every check passing AND `mergeStateStatus == CLEAN`, and stamp `NO REQUIRED CHECKS CONFIGURED:` on the detail string so the path is visible in the output rather than inferred from a bare "green". Everything else stays `None` and is still retried, so an auth error or gh output drift can never be mistaken for "nothing is required" — the gate fails closed on ambiguity, including an unreadable unfiltered query or an unreadable merge state. **Measure this script's exit code with a DIRECT run only:** `python3 scripts/ci/wait_for_checks.py <pr> > /tmp/out 2>&1; echo "exit=$?"`. Piping it (`... | tail -1; echo $?`) reports `tail`'s status — a `0` that looks like a pass. That mis-measurement already produced one retracted finding in this repo. **Granularity, unchanged and worth restating:** `gh pr checks` reports individual check runs (jobs), which is where the verdict is actually decided. Never gate on the run ROLLUP (a run reads `failure` when any job fails, including irrelevant ones) and never on `gh run watch` text (it prints step-level exit codes for steps inside jobs that still conclude `success`). For a raw run the job-level query is `gh run view <id> --json jobs -q '.jobs[] | (.conclusion) + " " + (.name)'`.

- **Husky's `commit-msg` hook shells to `npx commitlint`, which cannot run in a bare worktree and fails the commit** (2026-08-30, LIA-128/PR #61): a `git worktree add` checkout has no `node_modules`, so `npx` tries to INSTALL commitlint, finds no interactive consent, and aborts with `npm error npx canceled due to missing packages and no YES option: ["commitlint@21.2.2"]` followed by `husky - commit-msg script failed (code 1)`. The commit does not land. Nothing in that output names the real cause (a missing `node_modules` in this checkout), and the neighbouring `lint-staged could not find any staged files matching configured tasks` line reads like the actual problem while being harmless and unrelated. Fix: `ln -s <primary-repo>/node_modules <worktree>/node_modules` before the first commit in a fresh worktree, then re-run the identical `git commit`. A full `npm ci` in the worktree also works and is slower for no benefit. This bites every worktree created outside the `EnterWorktree` path, so expect it on any `git worktree add` used for a one-file fix.

- **A stale worktree registration whose directory no longer exists blocks `git worktree add` for that branch, and the error names the dead path as if it were live** (2026-08-30, LIA-128/PR #61): `git worktree add <new-path> <branch>` failed with `fatal: '<branch>' is already used by worktree at '/Users/…/.claude/jobs/<id>/tmp/<name>'` for a job directory that had already been deleted — `cd` into it returned `no such file or directory`. The message reads like a live peer session holding the branch (which is a real and common case here, and the right default assumption), so the safe move is to check before clearing: `ls -d <named-path>` plus `ListAgents`. Once the directory is confirmed gone, `git worktree prune` clears the registration and the `add` succeeds. Do NOT reach for `git worktree remove -f` or `-f -f` on a path you have not confirmed dead — see `~/.claude/rules/feedback_exitworktree_leaves_the_git_lock_held.md`, which covers the locked-but-live case and the reason `-f -f` is the wrong reflex.
