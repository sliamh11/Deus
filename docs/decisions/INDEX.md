Rounds 4-8 spent their entire effort on a proposed `--admin`-merge auto-forward fast-path, each round finding the previous round's version unsound in a new way — round 8 concluded this needs live-API integration testing, not further design review, and descoped it entirely to unconditional broker-routing. **After threat-modeler SHIP, the GPT code-review co-gate caught a real remaining flaw the entire 12-round threat-model process missed**: `--admin` is a `gh`-CLI-only concept invisible to a network-level proxy (GitHub's actual merge endpoint has no bypass-related parameter at all — verified against the REST API reference), so brokering only "`--admin`-flagged" merges while allowing "plain" ones through the routine credential doesn't work, since that credential's underlying account retains full bypass eligibility for every merge call regardless of CLI flags. Fixed: **every PR-merge call is now broker-tier, pinned to the approved head SHA**, with no CLI-flag-based distinction at all — naming the resulting throughput cost as a deliberate Phase 1 tradeoff, ambient-token rotation as the real structural defense against that cost being routed around (an explicit Phase 1 completion criterion, not an open-ended item), and deferring a well-tested auto-forward optimization to a separate future ticket. The retained direct-push-to-`main`/tag denial (round 7) now correctly covers both transports and tag refs (round 9), and the allowlist is transport-symmetric with it (round 10). Three further GPT-caught findings closed the loop: the Rollback section's suggested partial-revert path reintroduced the same flaw and was corrected; since every merge is now broker-gated and `release-please.yml` only fires on a commit landing on `main`, the release-via-ordinary-merge `NPM_TOKEN` vector is closed by the merge-brokering fix (not merely deferred) — only CI-secret-exfiltration (which needs no merge, just a PR open) remains genuinely open pending workflow-side hardening; and that closure claim itself needed its actual preconditions (§3's OS-isolation gap, §7's credential-retirement completion criterion) stated explicitly rather than left implicit, since without both, a compromised agent or leaked proxy credential bypasses the proxy/broker system entirely rather than being stopped by it. A subsequent GPT pass then found that completion criterion itself too narrow: this repo's own source (`src/index.ts:491`) loads a second, independent `GITHUB_TOKEN` env-var credential — rotating only the keyring token leaves that path (and, in principle, a GitHub-registered SSH key) equally able to bypass the proxy. §7's item was broadened to "retire every raw GitHub credential path an agent process can reach," not just one instance of it. **Two residual gaps remain explicitly unresolved, not glossed over**: a TOCTOU issue analogous to the already-fixed head-SHA one, for a merge's target base branch — GitHub's merge endpoint has no atomic "expected base" parameter to bind against, so the first attempted fix (re-check the base before merging) is itself still a narrower race, not a closed one; per-PR serialization between retarget and merge requests is named as the actual fix but not designed in this pass — and separately, the broker's own approval artifact (the existing unauthenticated verdict store) remains forgeable by the same OS user, a distinct gap named since early in this design and not closed by any of the above. Current recommendation: a local allowlisted API proxy (extending `credential-proxy.ts`'s pattern, agent processes never hold a raw credential) + human-approval broker (generalizing `approve_admin_merge`, reusing this repo's existing chat-channel integrations for approval dispatch), both requiring separate-OS-user isolation before containment holds; exact credential shape/count left for the implementation ticket, not finalized in this design pass (§7); workflow-side hardening named as a required, sequenced prerequisite (not solved by the proxy) for the CI-execution vector specifically.
